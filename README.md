# SolveBench

Benchmarking direct and iterative solvers for `Ax = b` on real sparse matrices from
the [SuiteSparse Matrix Collection](https://sparse.tamu.edu/), across domains that
include circuit simulation, computational fluid dynamics, and structural analysis.

CSE 402 (Numerical Analysis Lab) course project, BUET, Section A2.
Base paper: P. Khrapov and N. Volkov, *Comparative Analysis of Jacobi and
Gauss-Seidel Iterative Methods*, International Journal of Open Information
Technologies, vol. 12, no. 2, pp. 23-34, 2024.

The base paper derives exact convergence regions for Jacobi and Gauss-Seidel at
2 and 3 unknowns and validates them statistically on random matrices up to 5
unknowns. It never touches real data. This project asks whether its conclusions
survive on matrices practitioners actually solve, at sizes up to n = 10,000.

## What we found

Jacobi and Gauss-Seidel are usually taught with a clean guarantee: diagonal
dominance implies convergence, full stop. We tested that against 927 real sparse
matrices and ran into two problems the base paper's synthetic matrices never hit:

- 53% of the corpus has a zero on the main diagonal, which makes Jacobi and
  Gauss-Seidel undefined before a single iteration runs;
- even once a matrix is defined, the classical spectral-radius theorem only
  certifies convergence for the fraction of matrices that satisfy its
  hypotheses, and most real matrices do not.

We benchmarked sixteen solver methods (stationary, Krylov, direct, and
preconditioned families) against all 927 matrices to confirm both failure modes
directly, then built a diagonal-selection step: permuting which row of the matrix
sits on the diagonal, chosen by one of two competing objectives, before the
solver runs. Permutation alone recovers 199 previously undefined systems at zero
cost, with nothing lost:

| method | as given | with reordering | |
|---|---|---|---|
| Jacobi | 76 | **124** | +63% |
| Gauss-Seidel | 122 | **208** | +70% |
| SOR | 119 | **184** | +55% |

The remaining barrier, actual non-convergence once a method can be attempted,
proves largely resistant to reordering by either objective. The finding isn't
that the classical theory is wrong, it's that it answers a narrower question
than practitioners often assume, and the gap between the two is measurable.

Full writeup, methodology, and failure analysis: `Report/` is not included here
(course submission copy); see the project report for the complete argument.

## Layout

```
src/solvebench/          the library -- single source of truth for what runs
  config.py              every tolerance, cap and constant
  metrics.py             the one success predicate; applicability vs conditional success
  direct_solvers.py      hand-written Gauss elimination, Gauss-Jordan, LU, Cholesky
  iterative_solvers.py   Jacobi, Gauss-Seidel, SOR, CG, BiCGSTAB, GMRES, ILU
  reference_solvers.py   spsolve/SuperLU and the ILU-Krylov baselines
  reordering.py          convergence-oriented diagonal selection -- the proposed method
  refinement.py          iterative refinement, applicable to any solver
  spectral.py            rho(T_J), rho(T_GS) and the classical hypothesis classes
  benchmark.py           the 16 baseline methods
tools/                   build the notebooks, run them locally, draw the figures
tests/                   47 tests -- run before pushing anything to Kaggle
notebooks/               the 3 Kaggle notebooks behind the results above, with their
                         actual run output (main sweep, spectral analysis, reordering study)
results/                 tables and figures from the completed runs
```

Everything under `notebooks/` is generated by `tools/build_notebooks.py` from
`src/solvebench/`. Never edit a notebook by hand, that's how the library and the
notebook drifted apart once already.

## Method contract

Every solver returns `(x, iterations, reported_converged, work)`.

`reported_converged` is the solver's own opinion. It is recorded and never
trusted: `metrics.score()` decides success afterwards from the residual measured
externally from `A`, `x` and `b`, with one tolerance applied identically to all
methods.

`work` counts matrix-vector products, triangular solves and preconditioner
applications. This is the primary cost metric rather than wall-clock time, which
depends on the machine it's measured on, or iteration count, which isn't
comparable across methods (one ILU-preconditioned step does the work of many
Jacobi steps).

## Data

The matrix corpus is not in this repository. It can be re-downloaded from the
SuiteSparse Matrix Collection with `tools/download_corpus.py`.

## Running

```bash
pip install -r requirements.txt
python -m pytest tests/                  # verify the library
python tools/build_notebooks.py          # regenerate the Kaggle notebooks
python tools/test_notebooks.py 4         # execute every generated cell locally
python tools/make_figures.py             # redraw every figure from results/tables/
```

A `kaggle.json` API token is required to push notebooks to Kaggle. It is
git-ignored and must never be committed.
